# 内容与视听资源生产策略

## 基本立场

完整游戏需要主动生产内容和资源，不能只回接旧 Cocos 文件。剧情、任务、对白、地图、角色、美术、动画、UI、字体、音乐、环境音、音效和演出都纳入正式 backlog、预算和验收。

本策略不要求一次生成大量成品。先用代表性高质量样本确定方向、成本和技术规格，再按可审阅批次扩量。

## 生产轨

1. **世界与关卡**：区域结构、地图灰盒、交互密度、事件布置、导航、遮挡和性能。
2. **叙事与人物**：主线章节、支线、人物弧、日程、关系事件、对白、演出和文本 QA。
3. **环境美术**：TileSet、建筑、室内、自然物、季节/天气变化、光色和低档回退。
4. **角色资源**：场景 Sprite、方向/动作动画、表情、静态立绘差分和必要特效。
5. **UI/UX**：信息架构、HUD、菜单、存档、设置、输入提示、图标、字体和可访问性。
6. **音乐**：主题、地点、日常/调查/危险状态、过场与结局；优先验证可循环性和状态切换，再决定曲目量和分层方式。
7. **声音**：环境声景、交互反馈、脚步、工具、天气、生物、战斗动作/命中/敌人/UI 和响度/混音规范。
8. **本地化与发行内容**：文本结构、字体覆盖、商店图文、预告/截图和法律信息。

## 单项资源流程

`需求与语义 ID → brief → 方向样本 → 选择/修订 → 可交付源文件 → 运行时导出 → Godot 集成 → 场景验证 → 来源登记 → 质量/性能验收`

每个资源必须记录：用途、所有者、状态、源文件、运行时规格、来源/许可、审核人、Godot 路径、低档回退和依赖内容。状态统一为：

`needed`、`briefed`、`candidate`、`approved`、`produced`、`integrated`、`verified`、`deprecated`。

## 扩量规则

- 先完成一个代表区域、一个代表角色内容包和一套代表音频状态，再据实估算全量。
- 不因旧库已有文件就降低质量门槛，也不因新资源尚未制作就把正式游戏范围缩成旧 Demo。
- 大批量制作前冻结命名、画布/分辨率、动画状态、调色、循环点、响度、压缩和平台预算。
- 系统、关卡和资源同步设计；避免代码完成后才发现缺少关键动画、音效或叙事反馈。
- 任何采购、委托、AI 辅助或第三方素材都要有可商用证据、修改记录和相似性/来源检查。

## AI 辅助资源

- 先按玩法循环建立资源家族清单，再制作少量方向参考板检查覆盖、气质和一致性；不以零散生成数量衡量进度。
- 方向参考板默认不是 SpriteSheet、TileSet 或运行时资源，不得直接裁切进入 `assets/`。
- AI 候选必须经过人工重构、稳定命名、比例/透视/像素密度统一、透明切片、状态覆盖、相似性和来源检查。
- 地图、角色、UI 和音频分别执行其专属技术验收；“总表上看起来协调”不能代替 Tiled、Godot、动画或混音验证。
- 核心角色、Logo、主立绘与关键识别场景需要充分、可证明的人类创作和修改。
- 当前只采用离线生成、人工验收的候选生产轨，不在游戏运行时生成文本、图像或声音。
- 每批保留 Steam 预生成 AI 内容披露所需的工具、模型/版本、条款、输入、人工修改和最终用途记录。

完整参考边界与阶段应用见 `DESIGN_REFERENCE_LESSONS.md`。

## 存储与 Git

- 源文件、候选和审核导出长期保存在 D 盘 `art-source/`、`audio-source/` 或后续明确的内容源目录，并使用 `.gdignore`。
- Godot 只导入获准的运行时文件到 `assets/`；源文件不是运行时唯一副本。
- 大文件进入 Git 前先做资产盘点并确认 Git LFS、外部制品库或其他版本策略。
- 构建、缓存和临时导出不进入 Git；来源不明资源不得进入仓库或发行包。

## 验收层级

- **方向验收**：是否支持产品气质与可读性。
- **内容验收**：是否服务玩法/叙事、覆盖所需状态且无矛盾。
- **技术验收**：格式、尺寸、锚点、循环、透明边缘、导入、性能和低档回退。
- **法律验收**：来源、许可证、合同/授权、署名和 AI/第三方依赖记录。
- **场景验收**：在真实 Godot 场景、目标分辨率、目标画质和代表设备中验证，而不是只看源文件。

用户只需要参与方向、正史和高成本取舍；文件检查、导入、性能、覆盖矩阵和重复性验证由工程任务自行完成。
