# 完整游戏内容预算假设

## 用途

本文件给出可估算、可缩放的完整独立游戏生产包络，防止再次用旧原型文件数量代替产品规划。所有范围均为 P0 假设；P1～P4 测得单位成本后必须调整，P6 Alpha 前冻结。

## 世界与关卡

| 内容 | 初始包络 | 说明 |
| --- | ---: | --- |
| 主要生活枢纽 | 1 | 可由多个 TileMapLayer/室内组成，不等同单张旧地图 |
| 周边生活/采集区域 | 3～5 | 每区有独特资源、地标、事件和视听身份 |
| 调查/探索/战斗区域 | 2～4 | 必须承载战斗，是否沿用旧矿道由 P4 决定 |
| 可进入室内/功能场景 | 12～20 | 住宅、公共设施、经营与剧情空间 |
| 重要区域状态变体 | 每主要区域 2～4 | 剧情、季节、建设或异常变化；避免全量无意义换皮 |

地图数量不作为玩家价值指标。若较少的无缝区域能提供更好节奏，可以低于区间；若世界结构需要拆场景，可以高于区间。

## 角色与叙事

| 内容 | 初始包络 | 说明 |
| --- | ---: | --- |
| 核心常驻角色 | 8～12 | 有日程、立绘/表现、关系事件和主线/世界职责 |
| 支持/环境角色 | 10～18 | 有身份、日程或场景功能，内容深度分级 |
| 深度个人/关系弧 | 4～6 | 不等于全部必须可恋爱 |
| 较轻人物事件链 | 6～10 | 反映生活、职业、关系或世界变化 |
| 主线关键节拍 | 25～40 | 分布于完整旅程，不等同任务数量 |
| 可选事件/委托 | 40～80 | 以有后果或人物价值为准，拒绝纯跑腿灌水 |
| 源语言文本量 | 约 12～20 万汉字 | 完成内容管线后用实际每事件成本重估 |

旧 15 人可以进入候选池，但不会被整批保留或整批否决。

## 生活生产与物品

| 内容 | 初始包络 | 说明 |
| --- | ---: | --- |
| 作物/可培养品种 | 18～24 | 分季节/用途/成长策略，不只换数值与贴图 |
| 采集/矿物/特殊资源 | 20～35 | 服务制作、关系、调查和世界变化 |
| 食物/制作/任务产物 | 25～45 | 先确认制作/烹饪深度再扩量 |
| 工具及关键升级层级 | 5～8 类、每类 2～4 层 | 只保留能改变操作或规划的升级 |
| 经济/交换入口 | 3～6 类 | 商店、委托、建设或其他消耗口，避免资源失去用途 |

## 战斗内容

| 内容 | 初始包络 | 说明 |
| --- | ---: | --- |
| 玩家战斗风格/构筑方向 | 2～3 | 可以共享基础输入，但应产生可感知的策略差异 |
| 基础敌人家族 | 6～10 | 行为、轮廓和应对方式不同，不用纯数值换皮充数 |
| 精英/关键遭遇 | 3～6 | 用于检验组合、场地和成长掌握度 |
| Boss/主线战斗 | 2～4 | 与世界和叙事转折相关，不做孤立关底门神 |
| 代表性战斗场地规则 | 4～8 | 地形、危险、掩体或互动物按最终战斗形式调整 |

战斗包络必须在 P4 用一个完整遭遇测算动画、AI、VFX、音效、平衡和 QA 成本；可以缩减敌人/Boss 数量，但不能从正式游戏中删除战斗。

## 美术与动画

- 一个完整玩家角色包：四方向移动、基础交互/工具、受击或危险状态（若需要）、必要服装/状态策略。
- 核心角色 8～12 个完整场景 Sprite 与代表性动作；支持角色按内容层级减少动作但保持轮廓与日程可读。
- 核心角色每人约 4～8 个常用立绘表情/状态；支持角色约 2～4 个，最终由对白覆盖矩阵决定。
- 环境至少覆盖生活枢纽、周边自然、室内、调查区域、UI/图标和必要状态变体；不以每个季节全部重画为默认前提。
- 初始 UI 图标包约 60～100 个语义图标，先建立风格和可读性模板再扩量。

## 音乐与声音

| 内容 | 初始包络 | 说明 |
| --- | ---: | --- |
| 原创音乐/可循环主题 | 12～18 首 | 地点、日常、关系、调查、危险、关键演出与结局 |
| 环境声景/长循环 | 8～14 组 | 区域、天气/时间状态按实际系统决定 |
| 独立音效 | 80～140 个 | UI、脚步、工具、作物、环境、角色、调查、攻击、命中与敌人反馈 |
| 音乐状态/变体 | 4～8 组 | 优先复用主题和分层，不为数量而作曲 |

完整配音不作为默认范围。若采用语音，先用一段代表演出测算录制、剪辑、本地化和包体成本。

## 本地化与平台

- 简体中文为源语言；数据和 UI 从一开始支持文本扩展、字体回退和复数/格式化边界。
- 英文是否首发同步在 P5 前决定；没有完整文本预算、字体和 QA 前不宣称支持。
- Windows/Steam 是正式内容和性能预算基准；Web/微信另做包体、内存、纹理、音频与输入预算。

## 缩放顺序

产能不足时按以下顺序控制范围：

1. 删除低价值重复事件和视觉变体。
2. 减少支持角色和边缘区域，但保护核心人物弧与主线完整性。
3. 降低高成本系统广度，例如完整配音、战斗敌人/构筑数量、全季节重绘；战斗核心闭环不得整体删除。
4. 缩短总时长，同时保留开场到结局的完整旅程。

禁止优先砍掉结局、存档可靠性、关键视听反馈或内容 QA 来维持表面数量。
